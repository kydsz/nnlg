# 匿名评教异步标记缺陷：存量数据处理指引

> 本文件对应 GitHub issue #13 的验收项 4："存量错误标记记录有修正方案（迁移脚本或文档）"。

## 背景

Redis 异步提交链路（Redis Stream + 消费者）上线后，提交接口以 Go `bool` 直写
`is_anonymous` 流字段；go-redis 序列化为整数 `1/0`，消费者读取端返回字符串，
旧解析仅匹配 `"true"`，导致**凡经异步链路提交的评教记录 `is_anonymous` 一律为 0**
（即匿名评教被落库为实名）。修复见 `internal/cache/consumer.go` 的
`boolFromStream`（兼容 `bool true / "true" / "1"`）。

## 为什么不能写修正 SQL

`evaluation_record.is_anonymous` 为单一布尔列，且该缺陷下匿名与真实实名记录
**落库值相同（均为 0）、外表无任何区别**（无来源列、无旁路标记），因此
**没有可靠信号可以在事后区分"本应匿名的记录"与"真实实名记录"**。
错误的二进制标记无法机械回溯 —— 任何 `UPDATE` 迁移都会误改真实实名记录。

## 处理建议（评估后择一执行）

1. **接受现状（多数情况）**：确认业务上对该时间窗口内匿名身份泄露的可接受性。
   缺陷只影响"有 `evaluation:view_all` 权限者按数据范围查看/导出名单页"时的
   脱敏显示，记录本体仍保留评教人身份，未造成数据丢失。
2. **审计导出 + 人工复核（需要消除泄露时）**：
   - 依据异步链路**上线时间**起、`is_anonymous = 0` 的记录导出名单（含评教人、任务、提交时间）；
   - 由管理员按名单人工确认哪些应为匿名，逐条 `UPDATE evaluation_record SET is_anonymous = 1 WHERE id = ?`。
3. **上游改造**：如果评教提交页在提交请求中带有可区分布尔（前端 checkbox），
   可向前端确认该时间窗口内前端是否曾把匿名意图写入其它字段（如草稿表
   `evaluation_draft.is_anonymous`），若可关联则以草稿为准修正。

## 上线后确认

- 消费者解析已兼容 `"1"/"0"`；新提交的匿名评教落库 `is_anonymous = 1`。
- 建议上线后抽样：Redis 队列一次匿名提交，核对 `evaluation_record.is_anonymous`。
